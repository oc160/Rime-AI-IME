## 1. 结论（执行摘要）

**直接机制（三方证据闭环确认）**：IME 的 rime.lua 将 `io.popen`（同步、无超时、Lua 侧不可强杀的进程生成）放进了输入法关键路径——加载期冒烟测试与早期"每音节一键一次 `cmd+curl`"的候选过滤查询。本机进程创建路径在长 uptime（23 天）下存在间歇性永久挂起的缺陷，`popen` 一旦挂起，WeaselServer 即楔死；而 TSF 输入法架构下，应用每一次文本输入都是**同步 COM 调用**进入 WeaselServer——WeaselServer 卡死 = 正在打字的应用 UI 线程卡死；叠加"小狼毫被设为唯一输入法"后，单点卡死放大为全桌面雪崩。

**责任界定**：
- IME 开发侧：代码缺陷（关键路径 popen、无熔断无防抖）+ 运维失误（唯一输入法化、服务强杀）——**已认领并完成修复**；
- GPU 负载方：**无责**（首次冻结 18:26:38 早于其 18:29 的首个 GPU 任务 2.5 分钟；复现期间零 GPU 事件）；
- 机器环境：进程创建路径间歇挂起为放大器（非本项目引入，底层原因待查，已布防 dump 收集）；
- 系统硬件（电源/存储/GPU/网络）：**全部排除**，今日三次"崩溃"期间系统内核全程健康、未重启。

**中途假说修正（如实记录）**：系统排查方曾据"冻结应用均为打字类应用 + nvidia-smi 进程列表"提出"GPU 争用拖死输入法推理"假说。该假说被开发侧证据推翻：nvidia-smi 的 compute-apps 列表在 WDDM 下混合列出 D3D 图形上下文（explorer、TextInputHost 等均在列），WeaselServer 并不持有 CUDA；推理经 HTTP 走 CPU 实例。且 18:25 首次冻结发生时 GPU 尚无任何负载。`io.popen` 机制可完整解释全部三次发作及部署死锁，为最终定论。

## 3. 机制解析：为什么会"雪崩"

四级链式结构，每一环均有独立证据：

1. **同步无超时的进程生成**：Lua `io.popen` 无法设超时、无法从 Lua 侧强杀；挂起即永久阻塞调用线程。【应用日志】成功/挂起交替出现（成功：18:34:15、18:48:19 及基准期数百次 curl；挂起：18:25、18:53、18:54、19:01）——间歇性、状态依赖。
2. **TSF 输入法同步 COM**：【机制】应用每次文本输入都是无超时的同步 COM 调用进入 IME 服务。WeaselServer 楔死 ⇒ 宿主应用 UI 线程楔死。今日全部受害应用（Chrome、explorer×4、任务管理器、notepad、ZCode、quark）无一例外是**接收键盘输入的程序**；notepad 2 秒失响应是最强证词。
3. **唯一输入法 = 单点故障全桌面化**：【机制】仅存 IME 时所有文本框都路由到它。
4. **环境放大器**：本机进程创建路径（cmd.exe/conhost/安全软件钩子待定位）在 23 天 uptime 下间歇性永久挂起。这是"为什么 popen 会挂"的底层原因，非本项目引入，遗留待查（§7）。

**修复与验证**：移除加载期 popen + 卸除 filter 后（19:14），同机同输入法多轮打字零冻结；19:35 至今无任何 AppHang。对照组成立，因果闭环。

- 8/17 唤醒瞬间检出 `WindowsWcpStoreCorruption` ×3（组件存储损坏），提示存储数据完整性曾受扰。

**定性**：与本次 IME 事件**机制不同、路径不同**（睡眠电源转换 vs 用户态 popen），早于本项目两个月存在。首要嫌疑为 PCIe/NVMe 电源状态管理（当前电源计划 ASPM=中等节能；当前每日报错的网卡口即 ASPM 转换常客）。

**建议处置**（未执行，待用户批准）：
```
powercfg /setacvalueindex SCHEME_CURRENT SUB_PCIEXPRESS ASPM 0
powercfg /setdcvalueindex SCHEME_CURRENT SUB_PCIEXPRESS ASPM 0
powercfg /setactive SCHEME_CURRENT
```
另：查 GALAX XA1R 固件更新（现 ELFM01.0）；跑 `DISM /Online /Cleanup-Image /RestoreHealth` + `sfc /scannow` 修复 8/17 的组件存储损坏；处置前先做数据备份。
