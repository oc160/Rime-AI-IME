# AI 输入法（LLM 候选词重排）· 开发笔记

> 项目：把 rime-llm-reranker（macOS）移植到 Windows 并任务微调专用重排模型
> 位置：`F:\输入法`（训练/开发机：Tesla T10 工作站）｜打字主机：i5-13490F + RTX 2060
> 笔记日期：2026-10-13（覆盖 10-12 ~ 10-13 两天的完整开发周期）

---

## 一、项目目标与总体思路

**目标**：中文输入时，用本地 LLM 根据上下文把「正确的词」顶到第一候选，减少手动选词。

**总体思路**：输入法词库负责「产生候选」（它擅长召回），LLM 负责「裁判候选」（它擅长语义）——**重排层只做裁判，不做造句**。这个分工是整个架构的基石，后来所有设计问题都源于偏离或回归这个原则。

---

## 二、技术路线（三层架构）

```
① 候选生成层   雾凇拼音 rime-ice 词库
              整句组词 + 字词候选 Top5（召回强，语义弱）

② 重排层(v8)   librime-lua 异步 filter
              击键路径上只做微秒级文件读写（req.json / resp.json）
                    ↕ llm_rpc/ 文件握手
              sidecar 独立进程（请求泵，15ms 轮询）
                    ↓ HTTP
              llama-server（OpenAI 协议，本地推理）
              结果在「下一个击键」生效（异步设计）
              ◆ 推理服务死掉 = 安全直通词库，打字无感

③ 模型层      Qwen3.5-0.8B + LoRA(r=32, 全投影层) 任务微调
              训练格式 = 部署格式（提示词逐字一致）
              验收 = 40 条拼音歧义题：50%(裸) → 目标 ≥75%

数据飞轮      用户真实选择(USER_PAIR)自动入库 → Phase B 个性化原料
```

**演进路线**：
- **Phase A**（进行中）：0.8B 任务微调 + 上线换模型 + 放宽长句重排 + 恢复大词库
- **Phase B**：每日滚动个性化（夜间 LoRA → 黄金集回归闸门 → 达标换模型，replay buffer 防遗忘）
- **Phase C（终局）**：30-100M 拼音专用打分器（PinyinGPT 热启动蒸馏，ONNX **进程内**加载）——IPC/进程生成/网络全部归零，重排变成 1-5ms 的算术
- 可选增强：万象 n-gram 语法模型（进程内整句重排，0ms 兜底）+ 置信级联（小模型高置信直出 → 低置信升级 LLM）

## 三、架构演进史：为什么是 v8（最重要的章节）

### v6：macOS 直移植（io.popen + curl 同步查询）
- 移植时处理了 Windows 环境（路径/编码/引号），但保留了**同步查询在击键路径**的设计
- 在 2060 主机引发 4 次全桌面冻结 → 根因报告 `reports/incident_root_cause.md`

### v7：修补式加固（第一反应，方向错了）
- timeout 默认 0.3→1.0s、熔断器补盲区（200+垃圾body 也计失败）、删死代码、解析对齐
- 修复了 5 个移植 bug（`v~=nil and v or d` 把 enabled:false 读成 true、cmd 引号剥离、中文路径 ANSI 代码页等）
- **致命残留**：查询仍然同步阻塞击键路径 150-500ms

### 首次打字测试 → 冻结（v7 的判决）
隔离门禁全过（193 查询 0 失败），但**真实打字 40 秒后 explorer/ZCode AppHang**。三源日志交叉定位（rime_llm.log / llama-server 日志 / Weasel 日志）：

| 证据 | 结论 |
|---|---|
| llama-server 显示两次查询**服务端都成功完成** | 不是 popen 挂起（2060 第 1-3 次冻结的机制） |
| WeaselServer 日志截断在「loading default.yaml」半路 | 方案冷加载卡在击键路径（2060 第 4 次冻结的机制） |
| AppHang：explorer×2、ZCode（全是打字应用） | UI 线程被饿死 |

**机制**：TSF 输入法架构下，应用每次文本输入都是**无超时的同步 COM 调用**进入 WeaselServer；v7 把每个词 150-500ms 的模型查询压在这条路径上，打字应用直接挂起。叠加部署拉起的双服务器进程分抢会话。

**核心认知（这次事件最大的收获）**：
> 「门禁通过 ≠ 线上安全」——隔离回放验证的是功能正确性，验证不了「宿主应用 UI 线程能容忍多久的阻塞」。**在 Windows 输入法里，击键路径上任何超过几十毫秒的同步工作都是债务。**

### v8：异步文件握手（根治设计）
```
本键：  把查询请求原子写入 req.json（tmp+rename）→ 立即直通返回，零等待
下一键：读 resp.json（若有新鲜结果→应用重排；过期/缺失→继续直通）
sidecar 进程由部署方启动，绝不进击键路径
```
- 击键路径成本 = 一次文件读写（微秒级），**架构上不可能因查询冻结**
- 已知权衡：重排晚一键生效；词内落地率取决于推理延迟（GPU/训练后模型 → 60-150ms → 高落地率）
- 验证：T1（无 sidecar = 与纯基线耗时一字不差）、T2（122 请求全链异步零阻塞）、真实打字（18 请求 13 次重排生效 0 冻结）

## 四、基准与训练数据（数字备忘）

### 模型横评（40 条拼音歧义题，CPU single 模式）
| 模型 | 命中率 | 说明 |
|---|---|---|
| Qwen3.5-2B Q4_K_M | **80%** (32/40) | 教师档，零样本 |
| Qwen3.5-0.8B Q8 | **50%** (20/40) | 学生档 = 微调起点 |
| 结论 | single 模式（只出 1 词）全面优于 list 模式（更准更快） |

### 数据管线
- 语料：wiki zh 流式 713MB / 300 万段（`corpus/wiki_zh.txt`）
- 挖矿：`gen_synthetic.py` v2 —— 词库同音组出干扰词 + 真实维基上下文
- 15 万样本，**防泄漏过滤剔除 2011 条**（判据直接 import bench 的 CASES，评测与过滤永不脱钩）
- train 151832 / val 3098；5% 样本随机丢弃上下文（对齐线上无历史查询变体）

### 训练配方（含踩坑修复）
- LoRA r=32 α=64 全投影层（12.8M 可训练参数，1.7%）——**不做全参**：容量远未打满（loss 1800 样本就到 0.17）+ 共享 GPU 内存现实 + Phase B 换模型工作流依赖 LoRA
- **大词表 CE 显存坑**：15 万词表全序列算 logits = fp32 一步 1.93GB。修复：**左对齐 + `logits_to_keep` 只算尾部目标位置**，显存省 90%
- Qwen3.5-0.8B 是**混合线性注意力**架构：Windows 无 FLA 加速内核 → 参考实现慢 3 倍（3.68s/step @bs24）
- 梯度检查点 + expandable_segments：峰值压到 4.2GB，与共用显卡的其他租户和平共处
- 进度：暂停于 step 475/5000，loss 0.074（任务极易学）；已加每 500 步自动存档

## 五、黄金集设计（防过拟合原则）

**明确不做的**：拿「人生若只如初见」这类名句做验收——名句是词库和模型的熟面孔，测它等于测背诵，无泛化意义，还会诱导针对单句调参。

**正确做法**：
1. 从冷门诗词语料**随机采样** 500-1000 联（全唐诗/宋词随机抽，非人工挑选）
2. 经同音组挖矿生成样本（与训练数据同分布、不同实例）
3. 与 40 条 bench、train/val **三方互斥**（复用 prep_train_data 判据）
4. 分层覆盖：日常口语 / 新闻书面 / 专业词 / 冷门诗词 按比例
5. 用途：每轮换模型的**回归闸门**（不达标不换模型），不是调参目标

## 六、运维规程（血泪换来的纪律）

1. **部署三步**：先杀全部 WeaselServer/WeaselDeployer → 写配置 → 单次部署（部署器必须**脱离 shell 会话**运行，否则 bash 退出会连带杀掉它——「1 秒完成」假象的来源）
2. **预热交接**：冷加载发生在用户第一次切到输入法时（Windows 固有行为，无法根除只能治理）——部署完成后让用户做 10 秒预热动作（知情预期 2-5 秒一次性卡顿）再正式测试
3. **方案列表只留一个**：Weasel 部署器会把方案列表按**字母序**重排（luna_pinyin_simp 永远排在 rime_ice 前面），且 stock `user.yaml` 的「上次方案」会绕过 schema_list——要么删净，要么显式 select_schema
4. **双输入法并存是安全底线**：爆炸半径 = 一个输入法；用户随时 Win+空格 逃生
5. **共享资源意识**：这台 16GB 内存工作站与他人共用（9B 模型服务常驻 6GB 显存 + 5.6GB 内存）——页面文件固定 8GB 导致提交上限 23.4GB，训练需等对方下线（watcher 自动探测）

## 七、环境坑账本（都是真金白银的时间）

| 坑 | 现象 | 解法 |
|---|---|---|
| torch cu126 vs 12.2 驱动 | `is_available`=True 但建上下文报 46/500 错误；重启无效 | 降级 torch **2.9.1**+cu126 可用（2.14.1 的内核加载路径不兼容旧驱动） |
| Python 3.14 | cu118/cu121 无 cp314 轮子 | 无解，只能 cu126 起步 |
| llama.cpp 预编译 CUDA 包 | `invalid device function`（不含 Turing sm_75 内核） | CPU 版可用；GPU 推理需自编译或换卡 |
| 16GB RAM 机器 | CUDA 查询都报 OOM（WDDM 走系统提交内存） | 等共用租户下线 + `device_map+low_cpu_mem_usage` 流式加载 |
| Windows 中文区域 | PowerShell 输出小数逗号，Python float() 解析 0.0 | 输出整数再自己除 |
| 中文项目路径 | iso 回放里 lua 的 RPC 目录回退到 C:/Windows/Temp | lua 增加 `rpc_dir` 显式配置 |
| .git 只读文件 | rmtree 报拒绝访问 | onexc 里 chmod 后重删 |
| pip 装 torch 已有版 | 「已满足」跳过，+cpu 换不成 +cu | 先 uninstall 或直连 wheel URL（curl 下载 + **规范文件名**安装） |
| git 全局代理失效 | clone 连 127.0.0.1:1081 失败 | `git -c http.proxy= -c https.proxy= clone` |
| hf-mirror 下载 | curl 拼接 URL 时 `${f%%-*}` 截断仓库名 | 用 huggingface_hub API 解析准确文件名 |
