# 给输入法加大模型做候选重排：两天踩坑记录

**做了什么**：在 Windows 上把本地 LLM 接进 Rime 输入法（小狼毫 + 雾凇拼音）做候选词重排。思路很简单：词库出前 5 个候选，模型根据上下文把最合适的那个顶到第一，少手动翻页选词。

**第一次怎么做错的**：我把模型查询直接放在了打字的代码路径里。用户打完一个词，输入法同步等模型返回，一次约 300 毫秒。

隔离测试全部通过，193 次查询零失败。然后真人坐下来打字，40 秒后资源管理器挂了。

原因查清楚了：Windows 输入法架构下，应用每敲一个键，UI 线程都要同步等输入法进程返回候选，没有超时机制。我在这个路径上放的每个 300 毫秒，都直接卡住正在打字的应用。日志里模型查询全部成功返回，一行报错都没有——冻死应用的不是故障，是等待本身。

**怎么改的**：把查询从打字路径上彻底拿掉，改成异步文件握手：

1. 打完词，输入法把请求写进一个文件，立刻返回（微秒级）
2. 一个独立进程轮询这个文件，拿去问模型，把答案写进另一个文件
3. 下一个键落下时，输入法读结果文件，重排生效

打字路径上只剩两次文件读写。模型再慢、推理进程直接死掉，打字都不受影响，顶多重排不生效，词库顺序兜底。

改完后真实打字实测：零卡顿，18 次查询 13 次重排生效。

**其他要点**：

- 模型：Qwen3.5-0.8B + LoRA 微调。训练数据 15 万条，从维基语料用词库同音组自动挖出来，和测试集做了防泄漏过滤
- 基线：裸模型 40 条歧义题命中 50%，2B 模型 80%，微调目标 75% 以上
- 训练也有个坑：15 万的大词表算交叉熵，一步要 2GB 显存。改成左 padding + 只算答案所在的那几个位置（logits_to_keep），显存省 90%

**最大的教训**：测试全过不代表能上线。隔离测试验证的是功能对不对；真实环境验证的是别人能不能忍你。往别人的关键路径里放代码，按零容忍来设计——要么微秒级干完，要么异步出去，没有中间态。
